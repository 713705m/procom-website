01 — Algorithmique

Sélection de l'algorithme PQC

Analyse des candidats NIST post-quantiques et justification du choix de HQC pour le projet.

Contexte — Pourquoi la cryptographie post-quantique ?

Les algorithmes asymétriques actuels (RSA, ECC) reposent sur la difficulté de factoriser de grands entiers ou de calculer des logarithmes discrets. Un ordinateur quantique suffisamment puissant, via l'algorithme de Shor, casserait ces schémas en temps polynomial. Le NIST a lancé un processus de standardisation PQC dont les premiers lauréats ont été publiés en 2024.

Pourquoi HQC ?

🔢 Opérations simples

Addition = XOR, multiplication = Karatsuba sur GF(2). Idéal pour accélération matérielle ciblée.

⚙️ Adapté au FPGA

Structure quasi-cyclique adaptée aux architectures parallèles RISC-V + extensions custom.

🔓 Vulnérabilités documentées

Attaques DPA/CPA publiées (Huang et al.) permettant de valider la méthodologie de sécurité.

02 — Sécurité

Attaque CPA sur AES-128

Correlation Power Analysis sur l'implémentation AES de PULPino — récupération complète de la clé avec 200 traces.

Principe de la CPA

La CPA exploite la corrélation entre la consommation physique du circuit et un modèle de fuite. On cible la sortie de la S-Box lors du premier tour AES, en supposant un modèle de Hamming Weight.

ρ(HW(SBOX(p[i] ⊕ K)), W[t]) → max pour K = K*

Pour chaque hypothèse de sous-clé k ∈ {0…255}, on calcule la corrélation de Pearson entre le vecteur de consommation mesuré et le modèle prédit. La valeur maximale révèle l'octet de clé correct.

Setup expérimental

📦 Matériel

ChipWhisperer CW305 (Xilinx Artix-7) + CW-Lite pour l'acquisition. AES-128 sur PULPino (RV32IMC).

💻 Logiciel

03 — Algorithme

Algorithme HQC

Fonctionnement détaillé de HQC, opérations critiques et vulnérabilités exploitables par side-channel.

Qu'est-ce qu'un KEM ?

Un Key Encapsulation Mechanism (KEM) est un protocole cryptographique permettant à deux parties d'établir un secret partagé sur un canal non sécurisé. HQC est candidat NIST en remplacement de RSA/DH pour les échanges de clés résistants aux attaques quantiques.

🖼️ [ IMAGE — Schéma KEM générique : Alice / Bob / canal public ]

Structure mathématique

HQC opère dans l'anneau polynomial R = F₂[X]/(Xⁿ-1) :

Addition = XOR  |  Multiplication = rotation circulaire

La clé privée y est un vecteur de n=17 669 bits avec seulement 66 bits à 1 (très sparse). Cette sparsité est à la fois une force (efficacité) et une faiblesse (fuite d'information via la consommation).

KeyGen / Encap / Decap

🖼️ [ IMAGE — Diagramme détaillé KeyGen → Encap → Decap HQC ] Remplacer par votre slide ou schéma du rapport

Opération critique — Multiplication polynomiale

Le goulot de sécurité est la multiplication w = v ⊕ (u · y) lors du Decap. C'est là que la clé privée y interagit avec le ciphertext u, créant une fuite de puissance exploitable.

Technique d'attaque — Toeplitz / Ciphertexts choisis

En choisissant des ciphertexts u avec un seul bit à 1, on isole chaque coefficient de y un par un. 10 à 45 traces suffisent pour récupérer la clé complète (Huang et al., 2022).

Conséquences pour le projet

Performance

La multiplication polynomiale représente 84% du temps CPU → cible principale pour CLMUL.

Sécurité

La même opération fuit la clé y → cible pour l'attaque DPA en phase 2 du projet.

Principe — Carry-less multiplication dans GF(2)

Karatsuba logiciel implémente la multiplication polynomiale avec des shifts et XOR. Chaque clmul hardware remplace ~900 instructions logicielles (séquences shift+xor).

CLMUL(a, b) = a × b mod 2  ≡  XOR des décalages de a pour chaque bit 1 de b
🖼️ [ IMAGE — Schéma encodage R-type RISC-V de clmul_lo / clmul_hi ]

Implémentation RTL SystemVerilog

Architecture

Deux instructions : clmul_lo (bits [31:0]) et clmul_hi (bits [63:32]) du produit 64 bits. Cache micro-architectural 64 bits pour éviter le double calcul. Karatsuba hardware sur primitives clmul16, intégré dans PULPino via opcode custom.

Imprévu — Contrainte RAM

⚠️ Problème identifié

HQC-128 nécessite ~303 Ko de RAM (text=40 530 B, data=1 364 B, bss=808 B). PULPino dispose de ~32 Ko de RAM interne. Solution en cours : ajout RAM externe ou optimisation de l'empreinte mémoire.

05 — Simulation

Logiciel Gem5

Simulateur cycle-level pour le profilage RISC-V RV32IMC — identification des goulots d'étranglement de HQC.

Qu'est-ce que Gem5 ?

Gem5 est un simulateur microarchitectural open-source permettant la simulation cycle-level d'architectures CPU. Il permet d'obtenir des statistiques précises d'exécution sans nécessiter de matériel physique, idéal pour le profilage de code embarqué avant implémentation FPGA.

Configuration utilisée

ISA : RV32IMC
CPU : MinorCPU (pipeline 4 étages)
Gem5 v25.0.0.1 sur Ubuntu VM

Pipeline MinorCPU

IF → ID → EX → WB
Exécution in-order, CPI proche de 1
Adapté au profil embarqué PULPino

Toolchain RISC-V

Cross-compilation HQC

Compilateur : riscv32-unknown-elf-gcc-15.1.0 via PQClean, Makefile adapté pour RV32IMC. Fonctions d'entropie remplacées par des stubs déterministes pour la reproductibilité.

Problème RAM découvert par Gem5

⚠️ Découverte critique

C'est le profiling Gem5 qui a mis en évidence l'empreinte mémoire de HQC-128 : text=40 530 B, data=1 364 B, bss=808 B → ~303 Ko total. Incompatible avec les 32 Ko de RAM interne de PULPino. Gem5 a permis d'identifier ce blocage avant d'engager du temps hardware.
